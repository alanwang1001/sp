## 程式實作說明文件

### 1. 銀行存提款實作分析 (Bank Simulation)

#### 核心挑戰：防止競爭條件 (Race Condition)
在多執行緒環境中，當多個執行緒同時對同一個全域變數（本例中的 `balance`）進行讀寫時，會發生競爭條件。在高階語言中看似只有一行的操作：
```cpp
balance++; // 存款
balance--; // 提款
```
在 CPU 底層（組合語言層面）實際上會被拆解為三個步驟（Read-Modify-Write）：
1. **Read**：將記憶體中的 `balance` 值載入 CPU 暫存器。
2. **Modify**：在暫存器中將該值加 1 或減 1。
3. **Write**：將暫存器中的新值寫回記憶體。

若沒有同步機制，兩個執行緒在執行這些步驟時可能會交錯。導致其中一方的計算結果被覆蓋，造成「更新遺失 (Lost Update)」。這就是為什麼不加鎖時，執行完 100,000 次存提後，餘額幾乎不可能為 0。

#### 機制實作：互斥鎖 (Mutex) 的應用
為了解決此問題，我們引入了 `std::mutex mtx`，並在臨界區段使用了 C++11 的 `std::lock_guard`：
```cpp
std::lock_guard<std::mutex> lock(mtx);
```
* **自動化管理**：`std::lock_guard` 是一種 RAII 機制的實作。它在建構時自動呼叫 `mtx.lock()` 上鎖，並在生命週期結束時自動析構並呼叫 `mtx.unlock()`。
* **確保正確性**：這保證了在任意時間點，只有一個執行緒可以進入該區段修改 `balance`，最終輸出必定是精準且正確的 `0`。

### 2. 生產者消費者實作分析 (Producer-Consumer Problem)

#### 核心挑戰：執行緒間的協調與效能優化
生產者與消費者問題除了需要保護共享的緩衝區不發生 Race Condition 外，更核心的挑戰在於**協調執行緒的步調**：
* 當緩衝區已滿時，生產者必須停止生產。
* 當緩衝區為空時，消費者必須停止消費。
如果單純使用忙碌等待（Busy Waiting）的方式檢查狀態，會極大程度地浪費 CPU 資源。

#### 機制實作：條件變數 (Condition Variable)
實作中結合了 `std::unique_lock` 與 `std::condition_variable` 來達成高效的執行緒通知機制：
* **條件檢查與休眠 (`wait`)**：
  ```cpp
  cv_producer.wait(lock, [] { return buffer.size() < MAX_SIZE; });
  ```
  如果緩衝區滿了，`wait()` 會自動釋放互斥鎖並將目前執行緒置於阻塞休眠狀態，不佔用 CPU 資源。
* **主動通知 (`notify`)**：
  當消費者拿走資料後，呼叫 `cv_producer.notify_all()`。這會喚醒休眠的生產者重新獲取互斥鎖，並繼續生產。這種「通知-喚醒」機制完美解決了執行緒間的依賴與效能浪費問題。

### 3. 哲學家用餐實作分析 (Dining Philosophers Problem)

#### 核心挑戰：預防死結 (Deadlock Avoidance)
如果每位哲學家都採取簡單的策略：「先拿左邊叉子，再拿右邊叉子」，當 5 位哲學家同時肚子餓並拿起左邊的叉子時，每個人都會佔有左邊資源（Hold and Wait）且無法強行搶佔（No Preemption），同時等待右手邊的叉子，形成一個封閉的「循環等待 (Circular Wait)」。此時程式就會陷入死結。

#### 機制實作：多重鎖定演算法 (std::lock)
為了打破循環等待，本實作採用了 C++11 的 `std::lock` 全域函式：
```cpp
std::lock(forks[left_fork], forks[right_fork]);
```
* **原子鎖定 (Atomic Locking)**：`std::lock` 內部實作了死結防範演算法。它保證傳入的多個 Mutex 要麼**全部同時成功上鎖**，要麼就一個都不上鎖並原地等待。
* **結合 RAII 管理**：
  ```cpp
  std::lock_guard<std::mutex> left_lock(forks[left_fork], std::adopt_lock);
  ```
  使用 `std::adopt_lock` 參數告訴 `lock_guard`：「這些 Mutex 已經被上鎖了，只需要負責在作用域結束時幫我自動解鎖即可。」

透過這種方式，我們成功破壞了死結發生的必要條件，確保程式能順暢安全地執行完畢。
